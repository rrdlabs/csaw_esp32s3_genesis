board and the verification performed before delivery. It is the release
manifest for the merged artifact; the firmware source and build recipe remain

## 3. Flash

The board's USB-UART bridge must be enumerated (typically `/dev/ttyUSB0`) and
the ESP32-S3 in download mode. The merged image contains every region, so a
single write at offset `0x0` is sufficient.

```bash
# One-line esptool flash of the merged image.
# esptool v5: flash-mode/size/freq must come AFTER the `write-flash` subcommand.
python -m esptool --chip esp32s3 -b 460800 --before default-reset \
  --after hard-reset write-flash --flash-mode dio --flash-size 16MB \
  --flash-freq 80m 0x0 build/merged-binary.bin
```

Equivalent per-region command (generated by IDF, `build/flash_args`):

```
0x0      build/bootloader/bootloader.bin
0x8000   build/partition_table/partition-table.bin
0xf000   build/ota_data_initial.bin
0x20000  build/csaw.bin
0x420000 build/spiffs.bin
```

`scripts/flash_genesis_merged.sh` wraps the one-line command with a port
argument. `idf.py -p /dev/ttyUSB0 flash monitor` is the developer alternative.

## 6. Hardware verification — ATTEMPTED, FAILED (do not claim hardware pass)

A device appeared briefly as `/dev/ttyACM0` (Espressif USB JTAG/serial debug
unit, MAC `80:b5:4e:db:3c:90`, USB `303a:1001`) and the image was flashed to
it. **The flash succeeded, but firmware bringup on that device failed.** The
device then disconnected and did not return, preventing further diagnosis.

### 6.1 Flash — PASS

```
$ python -m esptool --chip esp32s3 --port /dev/ttyACM0 -b 460800 \
    --before default-reset --after hard-reset write-flash \
    --flash-mode dio --flash-size 16MB --flash-freq 80m \
    0x0 build/merged-binary.bin
Wrote 16711680 bytes (1431091 compressed) at 0x00000000 in 80.7 seconds.
Verifying written data...
Hash of data verified.
Hard resetting via RTS pin...
```
(exit 0; full log `/tmp/opencode/csaw_flash_genesis.log`)

An earlier attempt with the flash options placed **before** `write-flash`
failed with `No such option '--flash-mode'`. With esptool v5 those options must
follow the subcommand. The documentation and `scripts/flash_genesis_merged.sh`
have been corrected.

### 6.2 Boot / bringup — FAIL

Monitor log `/tmp/opencode/csaw_boot_monitor.log` (155 lines). The ESP32-S3,
8 MB octal PSRAM, 16 MB flash and the CsAW application itself boot correctly:

```
I (372) csaw:   CsAW - ESP32-S3 AI Agent
I (372) csaw_hal: I2C0 ready (SDA=15 SCL=14, 400000 Hz)
E (572) i2c.master: probe device timeout. Please check if xfer_timeout_ms and pull-ups are correctly set up
E (572) csaw_hal: IO expander not found at 0x20: ESP_ERR_TIMEOUT
E (572) csaw: Hardware bringup FAILED: ESP_ERR_TIMEOUT
E (1152) storage: SD card mount /sd unavailable; high-churn storage disabled
E (1152) csaw: On-device UI init FAILED: ESP_ERR_INVALID_STATE
```

A standalone I²C scan firmware (`/tmp/opencode/csaw_probe`, build log
`/tmp/opencode/csaw_probe_build.log`, monitor
`/tmp/opencode/csaw_probe_monitor.log`) probed addresses `0x01..0x77` on
SDA=15/SCL=14 at 400 kHz and 100 kHz and on swapped pins 14/15:

```
I (82) probe: bus sda=15 scl=14 freq=400000 create=ESP_OK
I (6032) probe: bus sda=14 scl=15 freq=400000 create=ESP_OK
I (11982) probe: bus sda=15 scl=14 freq=100000 create=ESP_OK
I (17932) probe: scan complete
```
**Zero devices responded** — not even AXP2101 (`0x34`) or PCF85063A (`0x51`).
The vendor reference (`examples/esp-idf/90_axp2101_pmu/components/board_variant/
board_variant.c`) confirms `0x20`, SDA=15/SCL=14 and 400 kHz are the correct
Rev 1 values, so the firmware configuration matches the board spec. The
failure is therefore consistent with the peripherals being unpowered/absent on
the attached device rather than a wrong address/pin in the HAL. This remains a
hypothesis: the device disappeared before a GPIO-level diagnostic could run.

### 6.3 Consequence

**Hardware has not passed.** The bringup order and 30 % brightness assertion
are verified in code and docs, but were **not** observed on silicon. The
operator chose to publish the secondary BSP repo anyway, explicitly labelled
with this failure. See [IMPLEMENTATION_PROGRESS.md](IMPLEMENTATION_PROGRESS.md).

## 7. What still needs a physical board

1. Re-connect a genuine Rev 1 board, confirm it is powered (USB and/or battery)
   and that the display backlight is active.
2. Re-flash `merged-binary.bin` at `0x0` (§3) and capture `idf.py monitor`.
3. Confirm the literal bringup log: expander → PMU → SH8601, with
   `brightness >= 30% asserted before UI`.
4. Confirm touch, audio, RTC, 1-bit SDMMC (`/sd/csaw`) and IMU probe lines in
   the boot log (see `docs/HARDWARE_BRINGUP.md`).
5. Confirm the on-screen keyboard/chat UI renders (see `docs/ON_DEVICE_UI.md`).
6. If I²C is still empty, check board power rails and whether the attached
   board is really the SH8601/FT3168 Rev 1 variant before changing firmware.
